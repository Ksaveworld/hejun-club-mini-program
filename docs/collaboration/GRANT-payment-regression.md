最终结果：15 tests，15 pass，0 fail，0 cancelled，0 skipped，进程退出码 0，总计 37.55 秒。前一轮不含赠送冲突的完整支付文件为 14/14，34.39 秒；两轮不重复计为不同用例。原 14 项继续不注入可选 resolver，保持原支付路径。`git diff --check` 通过；文件按协作规范使用 UTF-8/LF，支付适配文件原 CRLF 因此产生行尾差异，可用 `git diff --ignore-space-at-eol` 审阅实际逻辑变更。

新增或强化的关键分支：

- 权威未付款状态 0/1 允许本地取消，重复取消仅一次审计；保留签发记录与查单恢复标记。
- 取消后晚到的有效付款只保留一次 needs_reconciliation 收据，订单仍取消；不发会籍、奖励或发货请求。
- 渠道关闭时保留签发订单，不能生成新参数或跳过权威核验取消；恢复后权威状态 6 可以取消。
- 未知状态 11、不可取消状态 9、上游错误均保留订单及查单标记，不误发权益或误取消；上游凭据不外泄。
- 发货空 HTTP 200 但查单未发货时仍待重试；发货响应丢失但随后权威查单已发货时允许确认，付款与权益仍仅一次。
- 使用实际 `initializeGrantDatabase` 迁移和 `grant-host.mjs` 的真实 `grantPaymentConflict` resolver。分别测试 basic/star 赠送在收银参数签发后先落库、付款后到：微信流水号、金额及哈希关联的收据持久化为 needs_reconciliation，无付费会籍、奖励或发货；重复查单及重建服务保持同一收据，撤销赠送后继续查单也不自动激活，待对账审计仅一次。此处赠送使用明确标注的隔离合成行，验证支付与存储接入，不冒充后台批准全链路或真实资金到账。
- 保留所有原有凭证失败重试、身份/金额/环境校验、支付授权、支付与奖励原子回滚、重复查单、重启恢复、取消竞态及租约竞争测试。
