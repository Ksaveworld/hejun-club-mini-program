# UI与业务流程方法：从入口到办理结果

记录时间：2026-09-14。来源：U12界面改造、U13用户认可与会员功能验证。状态：本地网页验证，原生微信真机仍待验证。

## 先按用户要办的事组织内容

服务介绍回答“能帮我做什么”；企业名录回答“有哪些机构”。两者有关联，但不能把长篇服务介绍硬塞进企业筛选列表。可采用相邻页签，共享导航，各有清晰的内容层级。

本项目采用分类卡片→独立分类页→模块说明与价值→服务联系入口。卡片便于扫读，详情承接完整信息；不能仅有漂亮标题、没有可读内容，也不能把业务介绍变成“系统已提供”的承诺。

## 区分常驻功能和临时活动

临时问卷采用简短活动弹窗引导，长表单在独立页面填写。配置包括活动ID、起止时间和启用开关；关闭后不重复打扰，活动页保留再次进入方式，到期撤销入口且不保留空白。

适用条件是短期活动推广。紧急必读事项、持续核心任务或必须完成的流程不能机械套用“一次弹窗”。过期还要验证接口行为，不能只隐藏按钮。本项目服务端到期拒收，历史答卷保留给管理员。

## 一个功能要能走到结果

申请类功能至少包含：资格判断、填写与同意、服务端保存、重复提交保护、本人进度、运营处理、结果反馈。只有“提交成功”弹框，没有保存和后续处理，不能视为完成。

内容发布至少验证：谁能发、谁能读、失败重试、运营下架、作者看到原因、旧请求不会使已下架内容重新出现。业务人工前审后补，不等于放弃权限和运营处置。

## 以证据区分视觉提升和功能进展

每批分别说明用户看得见的变化、后台状态变化、验证方法和未完成部分。测试数量只是辅助；要能演示一条业务路径。网页通过不等于微信真机通过，本地构建不等于正式发布。

本项目证据：

- `tests/directory-campaign.spec.ts`：六类详情、再次进入、活动到期、首页无空白。
- `tests/business.spec.ts`：直接发布、运营下架、登录读取及订单流程。
- `tests/member-flows.spec.ts`：会员申请、后台跟进、本人看到结果。
- `tests/server/member-flows.test.mjs`：越权、重复、状态冲突、到期资格和历史记录。

## 保持迭代成本可控

内容放结构化资料，临时活动放配置，权限和最终状态由服务端控制。按业务边界拆模块，复用现有技术路线，避免为了整齐重写整个项目。数据库增量升级，回退保留历史记录。

复用时先核实新项目的角色、业务承诺和平台条件。此处沉淀组织方式与验证方法，不复用客户资料、会员价格、奖励比例、密钥或真实用户数据。
